### 1. 电力系统

电力单位：FE(Forge Energy)

#### Power Network V2：公平供电

同一已加载连通 Cable component 在服务器 `LevelTickEvent.END` 结算。producer 的机器 tick 先完成本 tick 发电并登记网络入口，随后 `energy/PowerCableTransfer.java` 扫描、聚合和分配，避免由第一个 producer 的 tick 顺序决定整网供电。

- 网络 key 是扫描得到的最小 `BlockPos`；每 Level / gameTime 保存已结算 key 和 cable 集合，重复 producer 请求不会重复结算。下一 tick 丢弃缓存，Level 卸载时清除，不维护永久 graph。
- 沿既有双向连接做 loop-safe BFS，最多 4,096 cable nodes，不强制加载区块。超出安全上限时整个扫描结果不结算，避免部分网络重叠发电；该上限是扫描保护，不是 FE throughput。
- 收集所有已连接端口的 ENERGY capability，并按位置/面及 storage 实例去重。`extractEnergy(MAX, SIMULATE)` 获取当前 producer 可用量；`receiveEnergy(MAX, SIMULATE)` 获取当前 consumer 需求，包含容量、速率和剩余 tick 预算。
- 只要 buffer 未满且 capability 可以接收，空闲或无配方机器也参与。满电设备不参与。
- 采用等份分配与剩余量重分配，需求已满足的 consumer 退出分配；按稳定端点顺序和 `gameTime % receiverCount` 轮转起点，避免整数余数长期偏向固定位置。producer 扣款起点也轮转。
- 每笔执行前重新模拟来源提取和目标接收，沿用服务器单线程 capability 安全约定；AFL 端口实际提取总量等于实际接收总量。第三方 capability 若违反自身 SIMULATE/EXECUTE 合约，沿用错误日志与回滚尝试，不能保证恶意或失约实现的事务语义。
- Cable 无 BlockEntity、库存、吞吐上限、损耗或 tier。Thermal 最大输出保持 16 FE/t；Energy Cell 充电模式只作 consumer、放电模式只作 producer，均保持原 128 FE/t 和模式持久化。
- 不经过 Cable 的现有直接相邻推送继续使用原即时路径；公平供电域是 Cable component。

| GameTest 场景 | 已验证结果 |
| --- | --- |
| 1 Thermal → 3 Crushers | 单 tick 为 6/5/5 的轮转；连续 3 个真实 tick 各累计 16 FE |
| 3 Thermal → 3 Crushers | 16 / 16 / 16 FE |
| 6 Thermal → 3 Crushers | 32 / 32 / 32 FE，各达到接收预算 |
| 4 Thermal；Crusher 只差 4 FE，另接 Reactor / Industrial Furnace | 4 / 30 / 30 FE，无剩余份额浪费 |
| Energy Cell 充电 / 放电、隔离网络 | 充电参与均分；放电 128 FE 分给 mixed consumers 为 32/48/48；两网不串电 |

服务器测试覆盖预算、重复结算与 FE 守恒。图形客户端综合网络场景尚未验证。

#### 加工机器能耗规则

- 机器 balance 定义 Energy Capacity、Max Input 与固定 Work FE/t。
- 配方只定义生产输入、输出和加工时间，不保存独立 FE/t 或总能耗字段。
- 每次加工进度成功前进 1 tick 时，机器扣除一次固定 Work FE；能量不足或输出堵塞时不前进且不扣能量。
- 单次配方总能耗是派生值：`Work FE/t × processing ticks`。

#### 能源线缆视觉连接

- 线段端点、转弯、分叉及机器接口处显示 Core 与对应方向的 Arm。
- 仅当一个线缆方块的两个相反方向都直接连接能源线缆、且不存在第三条连接时，使用贯穿整格的直线模型及独立无端盖贴图隐藏 Core。
- 该直线内部显示规则对 X、Y、Z 三轴一致；只改变视觉模型，不改变 FE 网络、连接判定或传输行为。

#### 化学反应器 V1 接口

- Chemical Reactor 背面是 FE 输入口，储能 `60,000 FE`，单 tick 最多接收 `128 FE`。
- 固定工作功率为 `32 FE/t`。服务器端按 `apocalypse_firstlight:chemical_reacting` 配方推进；断电、输入液不足、物品输出堵塞或废液槽容量不足时暂停，不耗 FE、不清零进度。
- 物品槽为 1 输入 + 1 输出；输出槽禁止玩家放入。完成时重新验证全部条件，再原子消耗 1 个物品与配方液体、产出物品和废液，内部配方液体结算不受外部端口 `25 mB/t` 限制。
- 玩家面对机器正面时，左侧为 `8,000 mB` 输入液槽且仅允许填充，右侧为 `8,000 mB` 废液槽且仅允许抽取；其余面不提供流体能力。
- Fluid Pipe 是无重力、高度无关的工业压力管道；AFL 标准自动流体端口统一为 `25 mB/t`。单个真实端口在同一 tick 内累计成功输入或输出最多 `25 mB`，多个源或多个目标不能叠加突破对应端口预算。
- Fluid Tank 自动化仍只从底部输出、只从顶部输入，水平侧不暴露流体能力；Chemical Reactor 左侧输入口是 fill-only 目标，右侧废液口是 drain-only 自动输出源，四个端口各自独立遵守 `25 mB/t` 预算。
- V1.5 固定接口外观：Fluid Tank 与 Chemical Reactor 不因 Fluid Pipe 连接状态改变接口模型或透明像素；管道直接连接接口表面。储罐外露顶底端固定使用 `fluid_tank_port_idle`，堆叠内部继续使用原 join 模型。储罐不再替代管道起始 Core，紧邻储罐的管段使用现有 Core + Arm；连接属性仍服务自动化逻辑。
- Fluid Tank 与 Chemical Reactor 均由源端服务器 tick 主动 push，复用同一套 capability 驱动的 BFS；路径可向上、向下或同高延伸。
- 管网优先选择当前可接受流体的目标；只有不存在可立即填充的目标时，才会选择容量已满或本 tick 输入预算已用尽、但端口与流体仍兼容的目标作为背压视觉路线。该路线继续刷新与正常输送相同的流体、方向 mask 和 20 ticks 保留状态，但本 tick 实际传输量为 `0 mB`，管道本身不保存流体。
- 当目标重新具备容量或输入预算时，同一路线恢复正常的 `25 mB/t` 输送；源流体耗尽、网络断开或目标端口/流体不再有效时停止刷新，现有视觉状态在 20 ticks 保留期结束后清除。
- V1.4.1：实际传输量大于 0 时使用当前 Fluid 的 FLOWING sprite；合法兼容目标暂时无法接收、实际传输为 0 的背压路线使用 STILL sprite。两者复用 Fluid 的 tint 与 atlas 动画，以 `isFlowing` 原位切换，不清空路线或改变方向 mask、保留时间。该视觉同步曾将协议从 `6` 升为 `7`；钨 V1 共用功耗同步升为 `8`，爆炸耳鸣 V1 新增定向 S2C 后当前 AFL 网络协议为 `9`。客户端与服务器须使用匹配版本；本次未改变流体传输或工业同步字段。
- 玩家手持 Forge 流体容器可从 Fluid Tank 任意成员方块的六个面操作统一逻辑储液槽；该手动容器交互不受自动端口 `25 mB/t` 限制。
- GUI 中液位使用当前 Fluid 的 still atlas sprite、tint 与实际储量比例渲染，并显示由共享 layout 定义的物品输入、炉式进度箭头和物品输出。FE、两槽流体、物品与进度均持久化；正常拆机时物品内容独立掉落，机器物品继续只保存 FE 与两槽流体。

#### Chemical Reactor Jade 与物品状态

Jade 接入现有 `AflJadePlugin`、`MachineJadeServerDataProvider` 和 `MachineJadeComponentProvider`。显示顺序是 Energy → Input Fluid → Processing → Waste Fluid → Output。Energy 始终显示；流体只在非空时显示整段；Processing 只在 `progress > 0` 时显示当前输入及 Jade 原生无字进度条，断电或阻塞暂停仍保留；Output 只显示真实非空产物，没有独立空输入区或 Running 文本。

服务器经 Jade 自身数据提供器发送 FE、两份含 amount 的 FluidStack NBT、8,000 mB 容量、真实进度/时间和非空物品；没有额外 AFL S2C。流体名称取 `FluidStack.getDisplayName()`。

流体条复用 `AflJadeFluidFillElement`：Jade `BoxStyle.DEFAULT` 先画容器，ProgressStyle 按 `amount / capacity` 给 overlay 内部填充范围；通过 Fluid client extension 的 STILL texture 从 block atlas 获取 `TextureAtlasSprite`，以 16 像素 tile 和变换后的 scissor 裁切末块，使用真实 tint。atlas 自行处理动画；不按 PNG sheet 计算帧。填充前 flush 已提交背景，沿用 Jade 当前 pose/Z，不增加任意 Z 偏移；finally 恢复 scissor 栈和白色 shader color。实际层级、动画、clipping 与 tint 的客户端观感仍待验证。

物品 Tooltip 由 `ClientFluidTankStoredFluidTooltip` 调用 `fluid/StoredFluidTooltip.java`，只读取已有 `BlockEntityTag`：Tank 的 `Fluid`，Reactor 的 `EnergyStored` / `InputTank` / `WasteTank`。Tank 显示名称和储量 / 20,000 mB；Reactor 显示非零 FE / 当前 FE 容量、非空输入液及废液各自的储量 / 8,000 mB。所有数值带千分位，单位只在末尾出现一次；未知 ID、损坏 ID、负量隐藏，超量按显示容量 clamp，hover 不修改 ItemStack。其它机器原有 FE Tooltip 和零值策略不变。

##### 实体交互音效 V1

Industrial Waste 继续保留自定义流体接触 / 移动触发层，因为它不属于 `minecraft:water`，不会自动进入 Vanilla water splash / swim 分支；SoundEvent、大小分界、pitch 与 swim 参数复用本地 Minecraft 1.20.1 Water 行为，splash 播放音量在 Vanilla 计算结果上乘 `1.25` 并限制最大 `1.0`。`apocalypse_firstlight:industrial_waste_splash`、`apocalypse_firstlight:industrial_waste_swim`、对应 `sounds.json` 项和正式资源 OGG 均已删除，不复制 Minecraft 音频，也不新增其它自定义液体交互声音。

源码 authority：本地 1.20.1 `Entity.doWaterSplashEffect`、`waterSwimSound`、`playSwimSound`、`getSwim*Sound` 与 `Player` 覆写。定义 `Q = sqrt(0.2F × vx² + vy² + 0.2F × vz²)`，随机 pitch `P = 1 + (randFloat - randFloat) × 0.4`（约 0.6–1.4）。

| 场景 | 当前触发 / 参数 |
| --- | --- |
| 入液 | Forge 接触高度从不大于 0 变为大于 0；沿用 firstTick 抑制出生即泡液的 splash，持续浸泡不重复，离开后重入可再触发 |
| 大 splash | `V = min(1, Q × scale)`；自身 scale=0.2，受控载具取控制乘客速度且 scale=0.9；仍以原始 `V >= 0.25` 分支。玩家用 `minecraft:entity.player.splash.high_speed`，其它实体默认 `minecraft:entity.generic.splash`；播放 volume=`min(1, V × 1.25)`、pitch=P |
| 小 splash | 同一公式且仍以原始 `V < 0.25` 分支。玩家用 `minecraft:entity.player.splash`，其它实体默认 `minecraft:entity.generic.splash`；播放 volume=`min(1, V × 1.25)`、pitch=P，无额外 pitch 变体 |
| 普通游动 / 涉水 | 读取原版 moveDist（碰撞后有效移动距离 ×0.6，Y 仅在可攀爬时计入）；超过独立音效游标后设为 `floor(moveDist)+1`。仅距离实际增加、允许 movement sound、非乘客、脚下判定非空气时发声，不改原版 nextStep / footsteps / game events |
| 游动声音 / 参数 | 玩家用 `minecraft:entity.player.swim`，其它实体默认 `minecraft:entity.generic.swim`；volume=`min(1, Q × 0.35)`，受控载具 scale=0.4，pitch=P。高速移动只通过更高速度音量及更快跨越距离游标体现，不再按 sprinting 人工增加 volume / pitch |
| 边界保护 | Silent 实体不播；同时接触原版水时优先原版水声音；非潜水船的乘客不额外 splash/swim，避免船内乘客接触误报 |

播放调用改为与 Vanilla 相同的 `Entity.playSound`：普通实体由服务器向附近玩家广播；玩家在客户端为自己播放、服务器广播时排除该玩家，因此同一监听者不会收到服务器和客户端两份重叠声音。该结论已按本地调用路径审计；多人客户端实际听感和双端无叠音仍待图形客户端实测。

桶继续通过 FluidType `SoundActions.BUCKET_FILL` / `BUCKET_EMPTY` 使用 `SoundEvents.BUCKET_FILL` / `BUCKET_EMPTY`；既有 Water ambient / drip 行为不变，paddle、bubble 等未另建触发框架。FluidType、water tag、禁补源、物理、水下雾、纹理、机器、管道、配方、世界生成、污染和辐射均未改变。

DEV 音效用例在 `src/dev/java/com/antaurora/apofirstlight/dev/IndustrialWasteAudioGameTests.java`，记录服务器事件并检查玩家 / 普通实体 small / high-speed splash、swim 的 Vanilla SoundEvent、速度音量、随机 pitch、次数、坐标、节奏、停止与 Silent 抑制；它不能证明客户端实际听感或多人双端播放。2026-09-05 隔离 GameTest Server 与 6 项流体、1 项雾判定回归合计 **8/8 通过**，日志为 `build/waste-water-audio-gametest.log`。正式 JAR 不含 DEV 类。

| 触发 | 读取实际 Camera.position 所在方块的 FluidState；FluidType 必须为 `industrial_waste`，且相机 Y 严格小于 `blockY + fluid.getHeight(level, pos)` |
| 覆盖 | 同时覆盖 `industrial_waste` Source 与 `flowing_industrial_waste` 的实际液面；恰好位于液面、液面上方、仅身体 / 脚入液、相邻空气均不触发 |
| 雾色 | RGB `(70,71,54)`，`#464736`；归一化为 `(70/255,71/255,54/255)`，低饱和灰黄绿 |
| 取色依据 | 原始 still PNG 全帧平均约 `(100,101,77)`，按 70% 压暗并取整；flow 平均约 `(104,105,79)`，同属灰黄绿。未改 PNG、alpha 或 Fluid tint |
| 距离与形状 | fog start=`1.5` 格、end=`10.0` 格，`SPHERE`；天空与地形雾使用同一参数，不修改区块加载距离 |
| 退出 / 重入 | 每次事件重新检查相机位置，不保存雾状态；离开废液后直接返回，交还原有世界 / 流体雾处理 |

接入当前 Forge 47.4.22 的 `ViewportEvent.ComputeFogColor` 与 `ViewportEvent.RenderFog`，仅 `Dist.CLIENT` 注册，优先级 `LOWEST`；RenderFog 设置距离与形状后取消事件，使 Forge 应用这些值。选择事件而非只覆写 FluidType 扩展，是因为本地 Forge 先调用流体扩展再发布视图事件：原有 `RadiationAtmosphereClient` 会把未映射为原版 FogType 的自定义废液当作 `NONE`，随后调整雾色。本实现仅在相机处于废液内时于其后设置专属参数，不修改辐射类或全局 FogRenderer。

Water / Lava / Powder Snow / 其它 FluidType 不通过该入口的类型检查；不添加 water tag，不改流体物理、禁补源、音效触发、机器或管道。没有 GUI / HUD / tooltip 绘制 hook，打开储罐界面本身不会触发水下雾；若相机本来就在世界废液中，界面后的世界仍可有雾，UI 本身不染色。Jade / JEI 及第三方渲染兼容仍待客户端验证。

实现文件（主代码前缀 `src/main/java/com/antaurora/apofirstlight/`）：`fluid/IndustrialWasteFog.java` 保存参数与不依赖客户端类的液面判定，`client/IndustrialWasteFogClient.java` 接入两个客户端事件。DEV 用例为 `src/dev/java/com/antaurora/apofirstlight/dev/IndustrialWasteFogGameTests.java`，不打包进正式 JAR。

验证结果（2026-09-05）：隔离 GameTest Server **8/8 通过**，新增用例检查真实 Source / 浅层 Flowing 的液面内外、10 次进出位置判定、脚部入液、相邻空气及 Water / Lava / Powder Snow / Air 排除；原有 6 项流体回归与 1 项音效回归同时通过，服务器启动未出现新增客户端类加载错误。日志：`build/waste-fog-gametest.log`。compileJava / processResources / build（offline）与 `git diff --check` 通过，DEV 用例不进入发布 JAR。

### 2. 矿石/金属

#### 钨 V1 生产线

| 步骤 | 机器 / Recipe Type | 输入 | 输出 | 时间 | 派生能耗 |
| --- | --- | --- | --- | ---: | ---: |
| 黑钨矿粉碎 | Crusher / `crushing` | Wolframite Ore ×1 | Wolframite ×1–3（闭区间均匀随机） | 200 ticks | 3,200 FE |
| 湿法处理 | Chemical Reactor / `chemical_reacting` | Wolframite ×1 + Water 1,000 mB | Tungsten Oxide ×1 + Industrial Waste 1,000 mB | 300 ticks | 9,600 FE |
| 高温还原 | Industrial Furnace / `industrial_smelting` | Tungsten Oxide ×1 | Tungsten Powder ×1 | 300 ticks | 7,200 FE |
| 粉末烧结 | Industrial Furnace / `industrial_smelting` | Tungsten Powder ×1 | Tungsten Ingot ×1 | 400 ticks | 9,600 FE |
| 压制钨板 | Compressor / `compressing` | Tungsten Ingot ×1 | Tungsten Sheet ×1 | 300 ticks | 4,800 FE |
| 合成碳化钨粉 | Alloy Furnace / `alloying` | Tungsten Powder ×1 + Coal/Charcoal ×1 | Tungsten Carbide Powder ×1 | 600 ticks | 14,400 FE |
| 硬质合金 | Alloy Furnace / `alloying` | Tungsten Carbide Powder ×1 + Nickel Ingot ×1 | Cemented Carbide Ingot ×1 | 800 ticks | 19,200 FE |

Industrial Furnace 的查询优先级为 AFL `industrial_smelting` → Vanilla blasting → Vanilla smelting。自定义工业冶炼的 `processing_time` 是实际 ticks，不乘原版配方使用的 `0.5` 系数；氧化钨和钨粉没有 Vanilla smelting / blasting JSON，因此不能绕过 FE 工业链。纯钨锭从 1 个 Wolframite 起算、不含矿石随机产量分摊时共消耗 `26,400 FE`。

Crusher、Chemical Reactor、Industrial Furnace、Compressor 与 Alloy Furnace 配方均由 RecipeManager 自动发现并进入各自 JEI category。JEI 加工时间读取配方，能耗读取服务器同步后的当前机器 balance 并相乘；Chemical 流体使用 JEI 原生 FluidStack 槽。代码与无界面配方/机器测试已通过，实际 JEI 页面、点击区域和 GUI 视觉仍待图形客户端验收。
