## 问题

用户 2026-10-08 发现：在 Fuel Stop A1 里，视角一转到后场就卡，Sundial 下最明显。

用开发用的渲染计时器（`client/AflRenderProfiler`）实测，Sundial 下：

| 视角 | 每帧总耗时 | 其中 AFL 方块实体渲染器 |
|---|---|---|
| 后场（库房、冷库一带） | 16–18 ms（55–60 FPS） | 约 11 ms：正常渲染约 4.6 ms，光影阴影约 6.7 ms |
| 天空 / 空地 | 6.4–7.7 ms（130–157 FPS） | 约 1.5 ms |

两个视角的差距几乎全部来自 AFL 的方块实体渲染器。

原因是"动画网格"类方块每一帧都在 CPU 上把全部顶点重新提交一遍。这类方块有冷柜、冰柜、三种门、收银机、配电盘、电表箱、垃圾桶等。开光影时，阴影还要再画一遍。

- 饮料冷柜每台每帧约 0.5 ms 正常渲染加 0.8 ms 阴影，3 台约 3.8 ms，是最大头。
- 冷柜的 1,162 个面里，有 974 个属于完全不动的柜体（`body`）。

货架、柜台、库房货架几乎不花时间：它们的本体已经烘焙进区块，货物这次也是空的。

## 测量方法

- **计时器**（`client/AflRenderProfiler`，只在开发环境生效；发布版可用 `-Dafl.renderProfiler=true` 打开）：
  - 每 5 秒往 `run/logs/latest.log` 写一行 `[AFL RENDER PROFILE]`；
  - 内容是光影包名、帧数、每帧耗时，以及每种渲染器每帧的调用次数和 CPU 时间（正常渲染 + 阴影分开）；
  - 带点的名字是渲染器内部的分段，它们的时间也包含在所属渲染器里。分段有：`plug_cord.all` 电源线，`mesh.cutout` 和 `mesh.glass_and_relit` 网格，`*.shadow_skipped` 被省略的阴影调用。
  - 这里只统计 CPU 往顶点缓冲里写数据的时间，GPU 绘制不在其中。
- **固定机位测量**（`tools/afl_minecraft_mcp/render_benchmark.mjs <标签>`）：
  - 通过建造工具的摄像机接口，依次把视角放到 6 个固定位置：库房、冷库、后墙外、营业区冷柜前、西门外、天空对照；
  - 每个位置停 16 秒，只取完全落在停留时间内的计时窗口，取平均；
  - 结果写到 `build/render_benchmarks/<标签>.json`。
  - 运行前提：游戏开着、创造模式第一人称、A1 建造会话已 resume、要测的光影包已开。
- **对比开关**（`client/AflRenderDev`，开发环境）：两步各有一个开关，可以在同一次游戏里切回旧方案，不用重启。
  - 客户端命令：
    - `/afl_render shadow_cull off|on|debug`；
    - `/afl_render static_mesh on|off`；
    - `/afl_render status`。
  - 测量脚本写 `run/afl_render_dev.properties`（键名相同），开发版每秒读一次。
  - 两个开关默认都是开。`static_mesh` 切换时会重建所有区块。
  - 计时器的每一行都写着当时生效的开关（`switches=shadow_cull=on,static_mesh=on`）。
- **A/B 测量**：`render_benchmark.mjs <标签> [每个视角停留秒数] [模式]`，模式用逗号分隔：
  - `current`：不动开关；
  - `off`：两个都关，就是旧路径；
  - `cull`：只开第一步；
  - `mesh`：只开第二步；
  - `both`：两个都开。

  每个视角依次跑完所有模式再换视角，这样所有模式看到的是同一个太阳位置。只统计开关和模式一致的计时窗口。跑完或者按 Ctrl+C 中断时都会删掉控制文件，开发版发现控制文件被删就恢复两个开关的默认值。时间最好先固定（关掉昼夜循环）。

## 第一步：阴影剔除（无损）

**原理**：
- 光影的阴影图每个像素只记离光源（白天太阳、夜里月亮）最近的表面深度。
- 一个方块实体如果每一处朝光源的方向都被完整的不透明方块挡住，那么在每条照到它的光线上，挡住它的方块都更近，它永远不会成为最近的那一层。
- 所以把它从阴影渲染里省掉，阴影图的每个像素都不会变。它能挡住的地方，前面那些方块本来就已经挡住了。

**引擎依据**（2026-10-08 读 Oculus 1.8.0 / Embeddium 0.3.31 字节码确认）：
- 装了 Embeddium 时，Oculus 的阴影渲染经 Embeddium 的 `SodiumWorldRenderer.renderBlockEntity` 调我们的渲染器。传进来的姿态是"阴影视图矩阵 × 平移到方块实体"，它 3×3 部分的第 3 行 `(m02, m12, m22)` 就是指向光源的单位向量：
  - 白天是太阳，夜里是月亮（太阳的反方向），所以 y 不会小于 0；
  - 已经包含光影包的 sunPathRotation；
  - 和 Oculus 自己算的光源方向对比，误差 2e-7。

  所以不用反射，在渲染器自己的变换之前读出来就行（`client/AflShadowLight`）。
- Oculus 在阴影渲染里对方块实体只做一种剔除：沿光源方向拉长的视锥。它没有任何遮挡剔除，Embeddium 的洞穴剔除在阴影里也是关着的，所以完全在室内的方块实体每帧都会画进阴影图，这就是可以省下来的部分。
- 阴影图每帧都重画，阴影渲染里的 `endBatch(type)` 不起作用。
- 阴影相机放在玩家朝光源方向 100 格处，没有深度钳制。比这更靠近光源的遮挡物会被裁掉，不在阴影图里。
- 光影包在阴影程序里做体素化（有几何着色器），或要求只按距离剔除时，Oculus 换成只按距离剔除的视锥，这时可能需要所有方块实体。Sundial 没有几何着色器，用的是默认的拉长视锥。

**判断**（`client/AflShadowOcclusion`）：对每一条光线都成立，不是抽样。第一版是在面上取点、每点一条光线，对抗审查指出这样会漏：阳光以接近 45° 穿过 1 格厚墙或屋顶上的开口时，光束可以窄到落在两个采样点之间，地上就会多出一条不该有的亮缝。现在的做法：
- 把渲染包围盒朝向光源的几个面切成边长不超过 0.5 格的小格，每条边最多 16 格（包围盒更大时格子跟着变大，判断只会更保守）。从盒子里任何一点射向光源的光线，都会从这几个面之一穿出去。
- 每个小格沿光源方向扫成一个棱柱，按光源方向的主轴一层一层往前走。只要有一层，棱柱在这层覆盖到的所有方块都是完整的不透明方块（`isSolidRender`），这个小格就算挡住：棱柱里的每一条光线都必须穿过这一层，而且就在覆盖范围里。只从"所有光线都会穿过"的那一层开始算。
- 玻璃、玻璃板、门、半砖、树叶等不完整或透明的方块都让光通过，所以窗户、玻璃幕墙、门口照进来的光都会被识别。Sundial 的半透明阴影也会把玻璃画进阴影图，所以玻璃不能算挡住。
- 方块只有真的在阴影图里才算数：
  - 从相机朝光源方向不超过 `min(64, 100 − 近平面 − 2)` 格；更远的会被裁掉；
  - 所在区块段没被 Oculus 的阴影距离盒（BoxCuller）剔掉；
  - 所在区块已加载。
- 走满 48 格还没有挡住的一层，或者走出建筑高度，都算照到了。只要有一个小格照得到，这个方块实体就照常画阴影。
- 结果按方块实体缓存。下面任一情况发生就重新算：
  - 光源转过 1° 以上，太阳换成月亮也算；
  - 相机移动了 8 格；
  - 渲染包围盒变了（比如拿起插头）；
  - 过了 40 tick（每个方块错开 0–7 tick）。所以拆掉屋顶后，最多约 2.4 秒阴影就会出来。
- 每帧最多重新算 8 个方块实体、查 12,000 次方块，轮不到的这一帧照常画，下一帧再算。
- 下面几种情况一律不省略（`client/AflShadowLight.setup()`，每帧读一次，反射读不到就不省略）：
  - 拿不到光源方向，或光源离地平线很低（高度角的正弦小于 0.03）；
  - Oculus 这一帧用的不完全是拉长视锥 `AdvancedShadowCullingFrustum`：它的子类"反向剔除"是给体素化光影包用的，要所有方块实体；
  - 阴影投影不是正交的；
  - 光影包关掉了地形阴影（`shadowTerrain`，屋顶不在阴影图里），或关掉了方块实体阴影（`shadowBlockEntities`；这时 Oculus 可能只为了收集发光方块实体才调渲染器）；
  - 方块实体的插头正被人拿在手里（插头跟着手走，会画到包围盒外面）。

**接入**：所有 AFL 方块实体渲染器都经过公共包装层（`client/AflBlockEntityRendering`）。在阴影渲染时先问 `AflShadowOcclusion`，可以省略的就直接返回。

**没核对的**：Sundial 有没有用 `block.properties` 让某些不透明方块不投影。如果有，这些方块其实挡不住光，会被误判成遮挡物。

**调试**：`/afl_render shadow_cull debug` 会在正常画面里给每个 AFL 方块实体画渲染包围盒：
- 红色：省略了阴影；
- 绿色：照常画；
- 灰色：还没检查过。

可以站在窗边、玻璃幕墙、门口、阳光照进来的地方，看判断对不对。

## 第二步：静态和动态几何分离

**三种方案比较**（2026-10-08 读 Forge 47.4.22、Embeddium、Oculus 的代码后得出）：

| 方案 | 每帧 CPU 成本 | 光影 / PBR | 风险 |
|---|---|---|---|
| 现在：每帧由方块实体渲染器（BER）提交 | 每个零件每个顶点，正常渲染一遍，阴影再一遍 | 正常 | 就是现在卡的原因 |
| 共享或缓存的 GPU 几何（顶点缓冲 + 每个方块实体一个模型矩阵） | 顶点不用重写，但每个方块实体每个零件每遍都要完整切一次光影程序 | 顶点缓冲必须在光影开着时按 Oculus 的扩展格式构建，切换光影没有通知，缓冲会失效（切线为 0，法线贴图错误）；在 BER 里直接画拿到的是 `gbuffers_entities` 而不是现在的 `gbuffers_block`；玻璃和补画发光排不进正确的顺序 | 高。光影下也做不到真正的实例化：Oculus 不支持，Flywheel 在光影下同样退回 CPU 提交 |
| 静态几何烘焙进区块（选用） | 0：只在方块变化时重建一次区块 | 走地形路径，Oculus 完整支持：图集 sprite 的 `_n` / `_s` PBR、切线、地形阴影；光影包切换时 Oculus 自动重建区块 | 静态部分必须由方块状态或模型数据决定；贴图要进方块图集 |

结论：用区块烘焙。GPU 共享几何只在区块烘焙落地后、动态部件的成本还很大时，才作为开发开关下的实验。

**第一版（冷柜原型）**：配置里列出不动的根零件（`baked: ["body"]`），只烘焙冷柜柜体。用户实机确认外观没问题。但第一次实机测试显示，剩下的大头是其他资产的柜体，以及静止时的门、盖、货物（见"第一次实机测试"）。所以第二版把这个机制做成通用的，`baked` 字段已删除。

**第二版：静止的零件交给区块**（`client/blockmesh/AflMeshChunking`、`AflStaticMeshModel`；细节见 [Animated Block Mesh Runtime](../rendering/animated_block_mesh_runtime_v1.md)"静止部件由区块画"）：
- 一个零件只要满足下面四条，它的不透明（cutout）几何就由区块画：
  - 动画通道停稳了，关着或开着都行；
  - 可见；
  - 不是全亮发光；
  - 父零件也满足这些条件。
- 玻璃、发光件、正在动的零件、电源线、柜里的通用货物仍由 BER 画。Sundial 下"玻璃后的发光件补画"不受影响。
- 每个方块实体在客户端主线程算出"区块该画什么"（零件、停稳的姿势、朝向、着色方式），作为模型数据交给区块模型。变化时请求刷新模型数据，并把它所在的区块段标记为重建。
  - 零件开始动或被隐藏时立刻请求；
  - 零件停稳时最快每 0.2 秒请求一次；
  - 一个方块 4 秒内请求 8 次以上（比如闪烁的零件），就 10 秒内不再往区块里加零件。
- 区块模型每烘焙一次就登记一次。BER 要等登记后再过 2 帧，并且姿势一致，才不画这个零件，所以零件不会消失。代价：零件开始动的那一刻，区块里可能还有 1–3 帧它静止时的那一份。
- 看不见的方块（0.25 秒内没在正常画面里画过）：正在动的零件直接按目标姿势交给区块。所以远处的门会直接跳到开着，不会消失。
- 每个客户端 tick 都重新检查正在动、或动画目标变了的方块，其他方块大约每秒检查一次（货物这类由方块实体数据决定的显示）。
- 着色：
  - 开光影时，顶点色为白色，由区块自己的方向明暗处理（光影包会自己照明）；
  - 不开光影时，把 BER 用的实体光照（两盏定向灯）直接算进顶点色，并关掉区块的方向明暗，这样区块画的柜体和 BER 画的部分亮度一致。这是对抗审查的意见：第一版不开光影时，朝东或朝西的冷柜，柜体比门框亮约 21%。
- 接入方式：
  - 方块改成 `RenderShape.MODEL`；
  - 方块模型 JSON 只写 `{"loader": "apocalypse_firstlight:static_mesh", "textures": {"particle": ...}}`；
  - `AflAnimatedMeshHost` 默认提供 `getModelData()`。

  2026-10-08 起 15 个网格资产都已接入：饮料冷柜、收银机、充电站、柜台通道门、冰柜、四色垃圾箱、两色玻璃双开门、配电盘、工业储物柜、铅箱、金属垃圾桶、电表箱、钢门、商用木门、自动售货机、饮水机。生成器同步了。
- 网格 BER 的可见距离从 64 格改成 128 格（`AflAnimatedBlockMeshRenderer.VIEW_DISTANCE`），因为区块在任何距离都画静止零件，玻璃、发光件和货物要跟得更远一点。

**需要实机确认的差异**：
- 区块的面按自己贴着的那一格取光照，BER 只在主格取一次，可能有一点亮度差。
- 开光影时，Oculus 可能对区块用带 mipmap 的采样，远处 UV 岛之间可能渗色（冷柜原型用户没看出问题）。
- 超过 128 格时，BER 不画玻璃、发光件和货物，静止的零件还在。
- 垃圾箱开盖时盖子伸出主格 1.27 格，超过 1.1 格的上限，这时盖子由 BER 画，关着时进区块。

## 第一次实机测试（2026-10-08，第一版）

用户开着 Sundial Lite v1.2.0 在 A1 里走动、转视角。下面的数据来自计时日志和 JFR。

- **卡的那些 5 秒窗口**（91 个，AFL 方块实体每帧超过 5 ms）：平均每帧 13.2 ms，其中 AFL 方块实体 8.0 ms。
  - 改之前同一带是 16.9–18.6 ms，方块实体 10.6–13.0 ms。不是同一个固定视角，只能粗略对比。
- **阴影剔除生效了**：冷柜、货架、柜台、收银机、冰柜、木门在阴影里全部被省掉，冷柜阴影从约 2.1 ms 降到 0。
- **还在每帧重画的大头**（每帧 ms，正常渲染加阴影）：

  | 来源 | ms |
  |---|---|
  | 冷柜门、灯、玻璃 | 1.70 |
  | 钢门 | 1.55 |
  | 电源线 | 1.17 |
  | 垃圾桶 | 1.03 |
  | 玻璃双开门 | 0.93 |
  | 冰柜 | 0.86 |
  | 木门、配电盘、收银机、电表箱 | 合计约 1.9 |

- **JFR 录了约 90 秒**（`jcmd JFR.start settings=profile`）：
  - 渲染线程的 Java 采样里，88% 在画方块实体，其中 76% 是 `AflMeshRenderer.renderPartsAtCurrentPose` → `BufferBuilder.vertex`。Oculus 给每个顶点补扩展数据的开销很大：`iris$beforeNext`、`fillExtendedData`、`computeTangent`。
  - 原生调用里 40% 是 `glBufferData`，也就是每帧把这些顶点重新上传。
  - 垃圾回收最长一次暂停 6.7 ms，不是主因。
  - 主线程上没有区块网格化。
  - 阴影判断只占 0.2%。
- **结论**：转视角卡，是因为货架那一带一转身，视野和阴影范围里会同时进来一批网格方块实体，它们的门、盖、柜体每帧都在重写顶点。所以第二版把所有静止零件都交给区块。

## 结果

第二版，用户 2026-10-08 实机，A1 里自由走动、转视角，两个开关都开。没有跑固定机位，也没有在同一局里切回旧路径，所以下面是不同视角的粗略对比：

| 版本 | 每帧总耗时 | AFL 方块实体 |
|---|---|---|
| 改之前，后场最卡的视角 | 16.9–18.6 ms（54–59 FPS） | 10.6–13.0 ms |
| 第一版，卡的那些窗口平均（91 个） | 13.2 ms | 8.0 ms |
| 第二版，Sundial 下全部窗口平均（27 个） | 9.95 ms（101 FPS，81–138） | 1.39 ms（0.66–1.84） |

- 第二版里 AFL 方块实体的剩余开销，每帧（正常渲染 + 阴影）：
  - 电源线 0.42 + 0.76 ms，现在最大；
  - 冷柜 0.31 + 0.65 ms，主要是它画的电源线和货物；
  - 饮水机 0.22 + 0.12 ms；
  - 玻璃和补画发光 0.12 ms；
  - 各种门、垃圾桶、配电盘、电表箱、收银机、通道门的网格部分都降到 0.01 ms 以下。
- 用户实机确认：外观、开关门和动画正常，"好太多"。

## 还没做的

- 电源线：现在剩下的最大一项（第二版每帧约 1.2 ms，含阴影）。它每帧重新计算路线、生成约 190 个四边形的管子和两个插头模型。线会伸出主格好几格，不能直接放进区块，下一步单独处理（缓存几何，或者按格子拆开）。
